# Knowledge Compiler（知识编译器）

一个给 AI 助手用的学习 Skill。你指定材料，助手先问清需求，再阅读提炼，最后交付学习笔记、规则（Rule）或 Skill。需求、过程记录和成果都保存在你的工作区，换一次对话也能接着做。

这份说明写给使用者，讲功能和用法。AI 助手执行任务时读的是入口 [SKILL.md](SKILL.md)，不需要读本文件。

- Skill ID 是 `knowledge-compiler`，显示名称是 Knowledge Compiler（知识编译器）。
- 阅读、判断和写作由你使用的 AI 助手完成。随包的 Python 脚本只核对文件、格式和记录，普通学习任务可以不运行它们。

## 1. 先了解三个概念

**轮次（Round）**：一次有独立交付目标的知识提炼任务。

- 只收集来源时先建立 `materials/`，这时没有 Round 是正常的。正式开始一次交付，才建立 `round-01`。
- 材料分几批到、并行采集、补采、草稿和返工，都不增加 Round。例如先收一批仓库，再补一批，又让几个子代理补采，之后反复修订和复验，只要最终只完成一次交付，就只有 1 个 Round。
- 一轮还没完成也没取消时，后来的材料都在这一轮里处理。上一轮已经完成冻结或明确取消，你又另外委托一次独立的提炼，才开下一轮。
- 取消的轮次保留编号和实际记录，但不算已验收的交付。
- 详细的判定规则见入口 §1、[R01](references/r01-task.md) §1.0 和 [R06](references/r06-learn.md) §3.5。

**总需求**：`requirements.md` 记录项目的长期目的、要交付什么（Skill、Rule 或两者）、总体范围和验收标准。第一次提炼时和你一起确认，以后的轮次直接继承，只问新增的部分。长期需求变了，要你确认新版本。

**累计成果**：`results/` 保存经你授权合并的当前成果。Skill 放在 `results/skills/<Skill ID>/`，Rule 放在 `results/rules/`。完成一轮不会自动更新它。

## 2. 它怎样工作

标准流程分五步，上一步没完成不会进入下一步。

| 步骤 | 助手做什么 | 留下什么 |
|---|---|---|
| 1 问清需求 | 第一轮确认长期目的、产物（Skill、Rule 或两者）、材料、覆盖范围、权限、深度和验收标准；以后的轮次只问新增的部分 | `requirements.md` 总需求，当轮 `checklist.md` |
| 2 确认开始 | 确认本轮要求，保存总需求的版本快照，核对材料确实能读 | `inputs/requirements.md`、`inputs/manifest.yaml` |
| 3 学习提炼 | 回到原文核对，处理新旧知识的冲突和适用范围 | `notes/`、`log.md` |
| 4 制作产物 | 交付这一轮完整、能独立使用的笔记、Rule 或 Skill | `rounds/<轮次>/output/` |
| 5 检查交付 | 逐项验收并冻结本轮输出；**交付 Skill 时再做 GQ1–GQ5 独立质量审查**；获得授权时逐条合并到累计成果 | 当轮完成记录、Skill 质量证据，按需更新 `results/` |

- 达不到约定的验收条件时，助手不会说完成。它会标出卡在哪里，并记下下次从哪里继续。
- 你只要求静态交付时，达到约定就可以完成并冻结这一版。真实任务效果、GQ5 和上线资格仍然标为 `NOT_PROVEN`。
- 先前失败的真实验收用例，必须在最终版上重新验证，不能只把修复单勾掉就说全部通过。
- 完成一轮不会自动更新 `results/`，也不会安装 Skill、修改你的个人规则或正式知识库。
- 你的一条完整请求或本任务已有授权，可以同时满足需求确认和开始确认。助手记录依据，已明确的目标和操作不重复询问；只有影响执行的实质缺口才补问。

最终产物在第 1 步约定，可以是：

- 学习笔记或材料整理。
- 规则（Rule）。
- 新建 Skill，或者改进已有的 Skill。
- Skill 加 Rule。
- 只给建议，不制作产物。

**轻量路径**：只做一份短笔记，并且你已经给出明确的来源和许可时，助手按入口 §2.1a 的轻量路径做。它在清单顶部写 `- 流程：轻量短笔记`，不要求两次确认、完整的总需求快照或整树指纹。笔记仍然放在当轮 `rounds/*/output/`，不能直接当作正式入库的证据。

### 2.1 复杂任务的几条规则

- **三个独立的选择**：学习深度（快速、标准、严格）、覆盖范围（全量、定向、轻量）和轮次方式（初始、增量、全量重新提炼、专项修订）各管一件事，互不替代。
- **全量学习**：你要求全量学习时，助手先列出完整的源单元清单（章、页、节等），再逐个实际阅读。抽样或检索命中不能证明全本已读。增量更新时比较来源身份和内容 SHA；同一章节编号的内容变了，也要重新读。见 R06 §3.6。
- **多个来源意见不一致**：按 [R17](references/r17-synthesis.md) 判断观点差异和各自的适用条件。
- **最终产物与中间记录分开**：Skill、Rule 和学习笔记的全部交付文件都禁止夹带材料引用、来源索引、书目、出处标记及他人项目或作品信息；附录、注释、元数据和 ZIP 也不能夹带。出处和规则映射只留材料/输入记录、当轮 `notes/`、`log.md` 等中间记录。成品内部导航、自己的规则编号和使用时定位用户当前稿件的字段可以保留，具体边界见 [R18 §2b](references/r18-consumer-operations.md)。
- **交付完整 Skill**：按 [R18](references/r18-consumer-operations.md) 写清触发条件、输入、操作、输出和失败时怎么办。来源里的知识要变成能区分的条件、反例和复杂操作分支。还要检查逐项填写的模板，以及模板和校验器是否对得上（支持标准 GFM 表格和 JSON Schema 的独立属性）。第 5 步另外核对 Markdown 结构和轮次收口。最终产物要能单独使用：不提来源，不写书名、作者、项目、链接、编号、年代、篇数，不引原句，知识写成通用、抽象的规则，例子自创；出处只留在工作区，有一处不合格就不能交付。
- **规则冲突**：只有 Skill 里确实存在互相冲突的规则和受保护的版本时，才在给使用者的参考文档里写清最小冲突集合、局部暂停、由谁裁决和修改后的回归检查，见 R18 §2d。普通笔记和简单的 Skill 不需要这套流程。
- **完成状态和指纹**：正式的完成状态只有“已完成”，“静态交付”写在验收范围里。单个 Skill 的身份指纹和整个 `output/` 的冻结指纹用各自的工具计算，不能互相顶替。
- 完整 Skill 的静态交付收口核对轮次根部真正的 `checklist.md` 和 `log.md`，不能用 `notes/` 里的副本替代；回执字段类型不符也会拒绝，格式见 R18 §7。
- 完整 Skill 的可填字段明确时，可以用只读的 `scripts/kd_delivery_preflight.py` 辅助核对。它会拒绝 `source_index` 配置、已知来源记录文件和出处标记；书名、引文及隐含归因仍须逐文件回读。它不能证明知识理解、宿主里的实际行为或模型收益。
- 仅交付 Rule 或笔记时，核对本轮清单、来源与版本、冲突和实际产物，再保存 `output/` 指纹并检查工作区；不调用完整 Skill 专用的结构、交付和 GQ 检查，也不伪造 `SKILL.md`。
- R17 和 R18 是写作规程，不是自动路由器，也不是效果评分或正式知识库的权限。

## 3. 工作区里会有什么

默认在当前项目的 `distillation/` 下建工作区，也可以指定其他位置。下面是简化示意，完整的目录树以 [SKILL.md](SKILL.md) §1 为准（包括第二轮的输入快照、可选的恢复基线和成果的内部结构）。

```text
distillation/
├── README.md                      项目工作区说明、职责和用法
├── AGENTS.md                      工作区长期执行约束
├── requirements.md                跨轮总需求（当前确认版）
├── materials/
│   ├── 2026-10-13/                原始材料批次（按日期及批次区分）
│   │   ├── manifest.yaml          来源身份、版本、摘要
│   │   └── ...                    原件/获准保存的附件
│   └── 2026-10-15/
├── rounds/
│   ├── round-01-2026-10-13/
│   │   ├── checklist.md           需求、权限、验收和进度
│   │   ├── log.md                 过程、断点和下一步
│   │   ├── inputs/
│   │   │   ├── manifest.yaml      本轮材料与总需求快照引用
│   │   │   ├── requirements.md    初始冻结的总需求副本
│   │   │   ├── revisions/         追加材料时保存同轮不可变快照（按需）
│   │   │   └── extracts/          必要的原文转换
│   │   ├── notes/                 中间分析（文件名自由）
│   │   └── output/                ★ 第一轮最终成果，验收后冻结
│   └── round-02-2026-10-15/       例：首次交付冻结后，另受托独立提炼
│       └── ...                    第二次独立完整交付
└── results/
    ├── manifest.yaml              当前累计版本、来源、文件摘要
    ├── skills/                    专放当前 Skill，逐项独立存放
    │   └── <真实-skill-id>/        占位符：必须使用产物实际 Skill ID
    └── rules/                     专放当前 Rule，不能与 Skill 混放
        ├── AGENTS.md              按需：已采纳的综合 Rule
        └── <真实-rule-id>.md       按需：其他独立规则，使用实际文件名
```

**命名和分组**

- 尖括号里的名字只是示意，不能照字面创建。Skill 目录名必须和它的 `SKILL.md` 里的 `name` 一致；Rule 的文件名要说明实际用途。`results/manifest.yaml` 登记的必须是真实路径。
- `skills/` 和 `rules/` 是真正的分类文件夹，有对应的成果时才创建。`results/` 根部不直接放 Rule 或 Skill。
- 旧工作区如果把 Rule 和 Skill 混放在 `results/` 根部，要按 R06 §4.13 经你授权后核对和迁移，不能直接改名，以免引用失效。

**各文件管什么**

- 工作区根部不要放旧草稿 `SKILL.md`，以免宿主误装。候选的种子材料放在材料区或草稿区。
- `materials/<批次>/` 保存每次采集的记录。批次不等于 Round。
- `checklist.md` 顶部的状态必须和真实的验收情况一致，`log.md` 记录过程。
- 一轮完成前，`output/` 可以反复修改；验收后按整树 SHA 冻结，以后不能回写。旧轮的输出不是 `results/` 的镜像副本。
- `results/manifest.yaml` 必须记录前一版的 SHA、每个文件的真实 SHA 和决策依据。
- 工作区的 `README.md` 写给人看，`distillation/AGENTS.md` 规定长期执行约束，两者都不记录某一轮的需求。
- 生成的 `rounds/*/output/AGENTS.md` 或 `results/rules/AGENTS.md` 是**规则产物**，不是本 Skill 的操作规则。有些宿主会按目录自动读取 `AGENTS.md`，生效前要核对它的作用范围，不能拿 README 里的说明代替宿主的隔离。

**原件和输入快照**

- 你指向的原件留在原处，只读不改；保留下来的材料批次不覆盖。
- 转换出来的内容记录来源，AI 的分析写进当前轮的 `notes/`。
- 开始提炼时冻结 `inputs/manifest.yaml`。同一轮里来了新材料，用 `inputs/revisions/manifest-vNN.yaml` 保存完整的有效输入和前一版的 SHA，不覆盖旧输入，也不因此新开 Round。
- 每次实际用到的来源和总需求版本，都要能按 SHA 重新核对。需求变化时保留旧版需求的冻结副本。

## 4. 安装

Skill 就是 `knowledge-compiler/` 这个目录，安装就是把整个目录放进宿主的 Skill 目录。目录名应当保持 `knowledge-compiler`，和 Skill ID 一致。

```bash
# 以 Claude Code 为例，安装给当前用户；在本目录的上一级运行
mkdir -p ~/.claude/skills
cp -R knowledge-compiler ~/.claude/skills/
```

- 只在某个项目里使用时，可以放到该项目的 `.claude/skills/knowledge-compiler/`。
- 拿到的是 `knowledge-compiler.zip` 时，解压出来就是这个目录。
- 更新时应当先移走旧目录再复制，避免旧版本里已经删除的文件留下来。
- 其他宿主请按该宿主的文档，把目录放进它的 Skill 目录。`agents/openai.yaml` 提供显示名称和简短说明，并关闭隐式调用；宿主是否读取这些字段，以实际宿主为准。
- 脚本只依赖 Python 3 标准库，不需要安装其他包。读取 PDF 需要本机已有 `pdftotext`。正式入库用的 `kd_write_txn.py` 和 `kd_publish.py` 依赖 `fcntl`，只能在类 Unix 系统运行。

## 5. 使用

第一次使用可以这样说：

> 使用 knowledge-compiler，完整学习我指定的仓库资料，提炼项目评审经验，输出一个 Skill 和一份项目 Rule，先整理并确认项目总需求。

第一轮还没冻结，又有新材料时：

> 向当前项目增补 `materials/2026-10-15/`，继续 Round 01：记录本轮输入快照的新版本，核实补采内容并返工当前输出。不要创建 Round 02，最终版通过验收后再冻结，并按授权更新 `results/`。

第一轮已经验收冻结，要再做一次独立交付时：

> 第一轮已完成，现在把新材料提炼为下一版完整 Skill，请启动 Round 02，保留并复核 Round 01 冻结成果，核对授权后再更新 `results/`。

助手会这样处理：

- 先确认你这次是只收集材料，还是要开始一次独立的提炼和交付。
- 开始 Round 01 时，按顺序补齐缺少的七类需求，并请你确认：学习目标、产物和位置、材料、覆盖范围和轮次方式、完成标准、允许的操作、学习深度。已经说清楚的不再问。
- 已有没完成的 Round 时，先接着做原来那一轮，不按阶段或材料批次另开。
- 你明确取消时，记为 `已取消`，并写上 `- 取消依据：<你的停止消息的位置>`。草稿保留，但不采纳。之后的独立委托使用下一个编号。
- 第一次获准建立 `results/` 时，`manifest.yaml` 写 `revision: 1` 和 `previous_manifest_sha256: null`。发现已有文件却没有索引时，先停下来核实。
- 目标有重大变化时，先请你确认新版本。每个输入版本的 SHA 和使用范围冻结在当轮的 `inputs/` 里。

### 5.1 权限和学习深度

- 默认读取指定材料、写获准的任务目录。其他操作先核对当前任务和宿主的已有权限，必要的本地验证按适用授权执行，不因整理清单再逐条征求同意。写总需求或工作区入口、更新 `results/`、修改其他源文件，以及联网、付费、安装、Git 提交和发布，仍须有覆盖各自范围的实际授权；缺失时才补问。
- 学习深度有三档：快速（整理并给建议）、标准（做出产物并做静态检查）、严格（再用真实任务对照）。选更深的档位不会带来额外的权限。

### 5.2 轮次状态

- 状态有六种：调查中、已确认、进行中、等待用户、已完成、已取消。
- **“已完成”要求有非空的完整输出和本轮约定的验收依据。标准流程还要有全部文件的真实 SHA 和整树冻结指纹，并且 `checklist.md` 顶部确实写着“已完成”。**
- 没完成的可以在同一轮里返工；已经冻结的旧轮不能回写。
- 取消只结束那一轮，不代表验收通过，也不代表授权回滚。

### 5.3 合并累计成果

- 本轮明确授权的 `results/` 合并可以一次做完，前提是目标范围没变、基线没有漂移、冲突已经处理。
- 纯追加时，保存旧索引、实际摘要和新文件清单作为恢复依据。覆盖或删除时，仍要先备份受影响的旧文件；证明不了能恢复就停下。
- 合并时逐项判断新增、修订、保留、废弃和待核实，并记录旧版的恢复路径、前一版 manifest 的 SHA、全部 Skill 和 Rule 文件的真实 SHA，以及决策依据。
- 每轮 `output/` 的全部文件按 SHA-256 清单和整树指纹冻结。本地自己写下的摘要不能当作外部的防篡改证明。
- 没有裁定的冲突不能合并。
- 个人 `results/` 里只有一个出处的观察，可以保留为待验证的经验，不受正式入库 N14–N16 的证据数量限制。累计更新不是正式知识库的晋升，正式入库仍然要经过 G1 和 S12。

### 5.4 交付 Skill 时的质量审查

按 [R09](references/r09-checks.md) §6 独立核查五项：

- GQ1 功能真实性
- GQ2 语义自洽
- GQ3 跨 Skill 接口
- GQ4 规则适用性
- GQ5 最终版真实任务

获准执行命令时，可以运行只读检查：

```bash
python3 <SkillRoot>/scripts/kd_artifact_quality.py --skill <Skill目录> --brief <冻结brief.json> --review <独立review.json> --evidence-root <证据目录>
```

- 有多个 Skill 互相依赖时，再加 `--peers-root`。
- 输出 `EVIDENCE_REVIEW_REQUIRED` 只说明记录的路径和字节前后一致，**不能证明审查是独立的、语义是正确的，也不能证明宿主里的效果**。
- 声称有自动化能力，必须有随包的实现和运行回执。缺少真实场景或独立审查时只能标 `NOT_PROVEN`，不能凭离线测试说质量合格。

### 5.5 工作区收口检查

获准执行命令时，可以在收口前运行：

```bash
python3 <SkillRoot>/scripts/kd_workspace_audit.py --workspace <工作区根目录> --expect-rounds 1
```

- `--expect-rounds` 填你实际委托的交付轮数，不算已取消的轮次；没有明确约定时可以不传。
- 它不写任何文件，返回 `PASS` 或 `FAIL` 和错误码。它能发现多轮没有收口、标准流程的输出缺少指纹、摘要漂移和成果混放。文件格式要求见 R01 §2.1 和 R06 §4.13。
- 状态、流程、冻结摘要等关键控制字段须唯一；重复声明会拒绝，不能靠第一处有效值掩盖后面的冲突。
- 它不能确认你的身份，也不能代替真实的业务验收。

### 5.6 尺寸限制和其他工具细节

- 本 Skill 不对 Rule、Skill 或参考文档设固定的尺寸上限。以前借用的限制都已撤下，包括入口 100/500/600 行、索引 120 行或 8 KiB、注入 8 KiB、描述长度和增长百分比。需要限制注入容量时，由调用方明确给出。对输入文件的资源安全保护仍然有效。
- Skill 结构检查和发布共用同一套 frontmatter 规则：平面的字符串字段，加上可选的 `metadata` 单层字符串映射。不再检查 500 行或描述至少 20 字。宿主是否支持这些字段，仍要实际核对。
- `kd_material_quality.py skill` 要求 frontmatter（到第一个独占一行的 `---` 为止）后面有非空白的正文，否则返回 `SKILL_BODY_EMPTY`（退出码 2）。它不要求固定标题或最少字数；正文非空也不代表内容可用。
- 子代理的数量按宿主的实际能力、预算和工作单元决定，不设 16 个的上限。
- 可选任务快照的 `revision` 范围是 1–9999，历史文件名也受同一上限约束；越界名称和版本断档都会拒绝。
- 大材料在脱敏后变长时，继续按安全大小分片。本地文件路径可以含字面的 `%`，路径隔离照常执行。
- 正式的命令行裁决必须明确传入 `--policy`，不会自动批准。
- 材料规范化使用 `kd-material-ops/9`。PDF 报告会保留提取时发现的无文本页，有缺口时返回 `NEEDS_REVIEW`。宿主要保存报告和原件的 SHA 并检查阅读范围；文本行检查通过不代表 PDF 全文已读。
- 不含会话结构键的普通 JSON（包括顶层数组）按文档处理；会话结构一旦声明，坏事件仍会拒绝，不降级成普通文档通过。
- 凭据扫描、脱敏和分片使用同一套识别范围：完整的 Bearer 令牌、数据库连接串里的用户信息和指定的私钥块。默认不输出正文。这些只是结构上的预警，不保证完全匿名。
- 更多细节见 R01、R02、[R03](references/r03-materials.md) §1 和 R09。

## 6. 它不做什么

- 它不是后台服务，也不是自动执行器。它不自带模型，不会自动采集材料。
- 它不会自动安装做出来的 Skill，也不会替你提交或发布。
- 没有用真实任务对比过，它不会说效果有提升。没有运行的测试，它不会写成通过。
- 质量预检不是模型评审器。自己填写的 JSON 不会因为通过预检就变成已认证的语义 PASS 或宿主 GO。
- 把成果写入带审批和版本记录的正式知识库是进阶流程，普通学习任务用不到。这个流程需要接入方自己提供可信的评测、批准和来源通道，这些通道没有随包提供。说明见入口 [SKILL.md](SKILL.md) 的 §2.2 和 [R16](references/r16-limits.md) 的 §5。
- 正式知识库中的 global Rule 写入须有两位不同的真实批准者，归档、恢复和会销毁内容的 `MERGE` 也不降为单人；这类 `MERGE` 仍保留 R2 确认要求。独立评测和来源回执仍须齐备，普通工作区成果不适用这个双人门。
