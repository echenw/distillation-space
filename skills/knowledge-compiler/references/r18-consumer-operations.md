# R18 — 面向使用者的 Skill 操作合同与按需路由

扩展入口第4–5步、R09 §6。**只在新建/更新完整 Skill 时按需读取**；学习笔记/Rule 不为凑目录增加操作模板。将来源提炼转成用户可以使用的任务行为，而不仅是读书摘要、主题章节或能力关键词。

## 1. 先问消费者能做什么

对重要操作逐项问：谁在什么输入下触发？哪些材料/状态确实存在？执行哪些判定分支？交付什么可回读结果？证据不足、权限冲突或失败怎么办？**不要只依靠22/10个要求ID都被提到来声称真正可执行。**

普通任务在 SKILL.md 应能选到一条最短执行路径；复杂分支再查必要 references。让消费者猜应读取哪十几个文件不能算有效的路由。

区分 workflow（Agent依照指令判断）、automation（随包真实脚本/Schema并有相应运行证据）、external（依赖目标宿主、外部系统及权限）。声明式YAML、CACHE、GRAPH或写在手册里的函数名称，不等于daemon、自动执行和缓存自进化已经存在。

## 2. 重要操作的最小合同

| 项目 | 使用者/审查者应能检验什么 |
|---|---|
| Trigger / negative trigger | 该用什么输入触发，什么相近但不适用的输入应排除？ |
| Input authority | 用户确认的事实F、基于来源的推断H、待决定的提案P有无混淆？ |
| Procedure | 条件→判断→行动序列；遇到分支何时补读哪份参考？ |
| Output / owner | 本Skill真实负责的输出结构与字段，哪些是建议、哪些已实际执行？ |
| Failure / fallback | 缺原文、错型输入、来源冲突、无许可、不可执行时怎样安全收口？ |
| Proof | 来源/任务要求如何支持规则，哪些检查已执行、哪些未证明？ |

F/H/P仅是方便审查的**可读分类**，不是宿主数据库、授权令牌或自动可信度系统；简单任务可显示“已知/推断/待确认”，无需强制输出冗长 JSON。现代字段来自USER_REQUIREMENT时如实标注，不假托古典来源。

至少区分“已完成/使用依据/未能核实/待使用者决定”。用户只要短回答时可以一段收口，不能为了填满模板而延长输出；仅参考文献说明不代替任务交付。

## 2a. 枚举需求的可填写模板：禁止“列出即算完成”

若用户要求独立记录 **N 项维度/步骤/字段**，先从确认的 requirements 中冻结 N 个唯一ID和对应消费者，再决定哪些结果需要逐项编辑、比较和复用：

- **用户将逐项填写或修改的结构**：最终 Skill 的模板或实际输出 Schema 对每个 ID 留下独立一行或独立字段，至少能记录值（允许未知）、F/H/P身份或状态、当前任务输入中的证据定位（有证据时，不是学习材料出处）、适用时间或版本（相关时）。不强制为不适用字段生造事实，不要求每项都填满。
- **仅用于阅读的摘要**可以分组；但不能拿“14项名称用斜线拼成一行”冒充14个可填写字段。Reference写了14项，不代表消费者拿到的模板可逐项编辑。双向关系、版本快照及跨章诊断尤其要保留独立标识与依赖。
- **反向验证**：只看最终 Skill 包，不借本轮 notes，逐项从需求ID找到可编辑字段、未知值处理和输出落点；14个独立维度只留一格标记 TEMPLATE_FIELD_ROW_MISSING，不得宣称“全部可填写”。
- **合成示例，非通用固定字段**：若需求是14维人物档案，可有14行如“CD-D01｜外貌｜F/H/P｜内容｜证据｜版本”“CD-D02｜气质｜…”，而非“D01/D02/…/D14｜逐项填写”。如果用户只要求总体摘要，单行不会成为缺陷。其它领域以各自真实字段清单为准。

## 2b. 最终产物自足，不提来源

不按任务或领域放宽。最终 Skill、Rule 和学习笔记都要能单独交给别人使用。成品只放通用的方法、条件、模板和自创的例子，禁止出现学习材料的引用、来源索引，以及他人项目、仓库和作品信息。检查覆盖全部交付文件，包括入口、参考文档、示例、模板、元数据、注释和附件，不能把出处挪到附录、隐藏注释或单独的随包文件来绕过。

- **只在中间记录保留出处**：来源索引、书目、参考项目清单、引文、来源 ID、作者、原文版本与定位、材料 SHA 和规则到来源的映射，只保存在材料/输入记录、本轮 `notes/`、`log.md` 等中间记录里。最终产物、成品目录和 ZIP 都不得夹带这些记录，也不放 `R13-CLAIM` 之类的出处标记。需要追溯时由审查者读取中间记录，不要求成品使用者回查。
- **不出现别人的项目**：上游仓库、参考项目、竞品和参考实现的名称、链接和路径不写进正文，它们特有的模块名、命名和设定也不照搬。学到的做法改写成通用的规则、条件和反例，例如写“检索结果先按相关度排序，再截断到预算以内”，不写“某某项目的召回模块是这样做的”。
- **不指向使用者拿不到的东西**：本轮 `notes/`、材料批次、原文库、工作区的 `results/`、本机绝对路径都不能出现，也不写“出处要回到某某材料去查”这类话。
- **不提来源**：正文不写书名、作者、年代、篇数，不引原句，不写“来源是……”“原文”“书内”“同书”这类话。从材料学到的知识改写成通用、抽象的规则；例子一律自创或写成抽象的情形，不复述具体作品的情节、人物和设定。规则的可信度和限制照样写，只是不借来源来说明。
- **隔离回读**：交付前只拿 Skill 包，不提供本轮 notes，把正文读一遍。读者要去包外查才看得懂的地方，记 EXTERNAL_NOTES_REFERENCE；出现来源、作品、作者、别人的项目名、仓库链接或路径的地方，也要记下。两种都要在冻结前改写，不凭作者记忆补充说明。有一处不合格，本轮 `output/` 就不能冻结，也不能合入 `results/`。
- **逐文件检查清单**：书名号里的作品名、作者和人名、项目和仓库名、链接、编号（如 PG 号、行号）、年代和篇数、材料原句、“原文/书内/同书/来源是”这类字样、“旧版/本版/更正”这类改动痕迹。删除来源后要通读改过的句子，不能留下空括号、悬空的“见”“据”“与 同”和空表列；删除时不能误删产物自己的编号（如修改级别 L0–L4）。
- **区分出处与正常操作**：成品内部的文件导航、规则编号，以及使用时定位用户当前稿件的字段，不是学习材料的出处索引，可以保留；不得借这些字段带回他人作品、材料编号或包外来源路径。可信度、适用条件、限制和反例必须保留，但用通用表述，不以来源数量或名气作背书。
- **跨领域示例**：从合同 v3 提炼审核 Skill，规则写成“付款条款要写明触发条件和期限”；合同版本、页码和条款编号记在本轮 notes/，不写进 Skill。

## 2c. 操作示例要有独立判断，不能只复制最终正文

对重要且复杂的操作，在本轮 notes/ 中留至少**一条具体输入 → 条件判断 → 预期可检查输出**的示例；若 Skill 使用者需要示例才能执行复杂分支，最终 references/ 留最短合成例子及失败出口，不装入内部审查日志。

- R17裁决对每项重要冲突必须作唯一明确的候选决定、采用条件、至少一个不采用或待决分支及理由。不能七项都写“ADOPT 或 CONDITIONAL”然后不选择。
- **DESIGN_EXAMPLE** 只是说明怎样用；没有隔离真实模型执行不标 ACTUAL_TASK_OBSERVED，没有独立非作者评审不宣称GQ5 PASS。真正下游证据仍遵 R09 §4–6 的统一题、原始输出与最终树SHA。
- notes/operations-contract.md 不得只是 SKILL.md 全文副本。至少指出一个真实会失败的用户输入、对应保护分支和后续需要如何验证。

## 2d. 复杂任务的操作深度：表格可做目录，不能代替工作流

**先判定任务的复杂性，不按领域或版本固定页数。** 如果操作涉及多步判断、互斥规则、版本状态、作者正典、多轮修订或会造成不可逆结果，就不能仅有一行“输入/动作/输出/异常”。入口中的单行路由表可以保留，但其指向的reference须足以让**另一个没看生产笔记的Agent**独立执行。

对每个真实复杂任务或共享一套判据的相近任务群，从确认的 requirements 逐一检查：

- **判断标准**：哪个可观察事实触发哪一分支？哪些证据足以支持判断、哪些是反证、哪些仅为作者偏好或信息缺失？不写无法应用的抽象正确性口号。
- **执行过程**：解释阶段顺序、依赖事实、候选替代方案、具体输出字段和需要时的补读；版本、授权、无法同时满足的规则必须有独立出口。
- **诊断与修订闭环**：能指出问题所处原文/对象位置、受影响的规则、最小修法及修后回归检查；不能只写“优化质量”或“尊重上下文”。
- **代表性难例**：根据真正的分支风险给一份虚构但具体的输入 → A/B条件 → 输出/失败 → 复查示例；设计例只标DESIGN_EXAMPLE，实际任务必须真实运行后才标OBSERVED。只要情况性质不同，应覆盖不同困难类别，而不是同一例子换9个标题。
- **负面回归**：确认它不会因新增模板而把原本可执行的深层规则压成摘要。首次编写不要求先读竞争作品；只对**当前输入需求和自己编写的源证据**检查是否遗漏可观察判断。

例如小说的规划、写作、改稿、审稿本来就是不同任务：规划需有因果/伏笔/章间状态检查，写作需有POV与信息许可/风格落地，改稿需有原句定位/最小修改/回归，审稿需区分诊断证据/严重度/作者豁免。卡片生成、诊断、修订也需要区别自己的约束状态和版本冲突，不能“九项都列名”即自动通过。

**仅当需求确实存在互斥约束、受保护原文或多版本状态时**，消费者参考文档还须讲清楚：先核对同一对象的有效版本、范围、时点和同级规则；若不能同时满足，列出具体规则引用构成的最小冲突集合，由有权者裁决，禁止擅自覆盖锁定内容。只暂停冲突及其直接依赖部分；无依赖且已获授权的其余工作可以继续，但不得把局部成功报成全局PASS。获得明确选择后保留旧版和差异，复核直接消费者与原约束。缺信息时明确待核，不发明卡片注册表、权威状态机或通用优先级。这是 R17 条件判断向最终使用者的投影，不是所有Skill默认需要 `card_id`、`canon_version` 或 hard/soft。

**格式、引用与深度按两层分别验收**：机器可以核对任务ID、Markdown表格和结构完整；无法判断专业分支是否足够。因此GQ1/GQ2/GQ4的独立语义审查须给出一个具体复杂输入的分支对照与最终reference定位，未实测不得写GQ5 PASS。不要设置最低段落数、字数或文件数来制造假深度。

## 3. 按需加载与邻接补读

在新 Skill 入口建立小型任务路由表。建议写“任务 → 首要参考 → 需要时补读的关联参考 → 无来源/文件时的出口”，避免加载整个内容库；**这些只是文字导航，不是自动引擎。**

对 Knowledge Compiler 自身：

| 情况 | 优先 | 补读条件 |
|---|---|---|
| 一份来源的普通学习整理 | R06 | 真实性争议时R05/R09 |
| 多份来源观点冲突 | R06 + R17 | 涉及规则归纳时R07，证据绑定时R09 |
| 新建/升级完整Skill | R18 | 来源融合用R17，成品检查用R09 |
| 原有规则故障 | R10 | 需要真正比较行为时R09/R11 |
| 正式知识入库 | R02/R12 | 不省略所有S10/G1/S12的既有门禁 |

默认只加载相关文档；遇到新依赖再补一份或多份，**不设未经实测的固定top-k**。省token是潜在好处而非已观察事实。路由文件不存在、关键事实没读到或边界不清时，不得依靠“缓存可能知道”补造依据。

## 4. 交付前遗漏/误触发六问

这些检查记在当前轮 notes/；仍使用 R09 GQ1–GQ5 的唯一门禁，不另造“自动质量检测”：

1. 触发：有没有相近但不应该调用的用户请求？负向触发与职责边界是否清楚？
2. 缺料：没给正文、日志或代码时，是否会编造引文、验证回执或已完成动作？
3. 冲突：互斥事实、不同版本或相反来源出现时，有无定性、条件和最终决定者？
4. 权限：授权分析会不会被解释为允许安装、写文件、发邮件或正式知识提交？
5. 格式：模板与脚本是否接受一致的数据格式？不合法JSON类型会不会静默误报PASS或抛无界异常？
6. 消费者：当入口声称存在状态机、registry、后台调度或跨Skill消费接口，是否有真实实现/提供方？

有实测失败才写 FAIL；只有文件/静态结构写 STATIC_CHECKED；独立调用尚无回执则 NOT_PROVEN。至少为关键复杂能力选择正常、缺料、冲突、边界案例，先冻结测试标准，不能用作者自己的模型自评分证明收益。

## 5. 两个合成示例

**例A：客服政策材料→回复Skill。** 用户只提供退款政策的摘要，但要起草退款回复。错误：“自动核查订单并成功退款”。合格合同：输入=确认的政策片段、实际订单证据（如有）；动作=判断是否可提出退款回复；输出=草稿、需要补充的订单信息；无真实订单只说无法核实，**不得声称支付系统已退款**。如果用户确实要求执行退款，需独立授权和真实工具。

**例B：软件README与代码→排错Skill。** README说“超时就重试”，代码却有未知结果的幂等保护。错误：“所有超时直接重试”。合格合同：锁定同版本可读代码与README，未执行/未知结果分开；未知结果时先检查receipt，禁止盲目重放不可逆动作；没读代码就标H/NOT_PROVEN而不装作实现已确认。这里不是授权真正对线上服务重试。

真正的可用性必须由真实消费者运行、冻结判据、结果回执与非作者复核确认（R09/R11）。本文件只能帮助改进**结构化行为合同**。静态结构通过不能证明真实任务效果提升，不宣称凭文档长度或route表就提升了模型结果。

## 6. 可选的只读交付结构预检

有明确**枚举可填字段**时，可以在本轮 notes/delivery-preflight-spec.json 中记录要求（该 spec 不需要随生产 Skill 分发）。`templates[]` 中默认以 Markdown 表格校验 `.md`，以 JSON Schema 校验 `.json`，也可指定 `format: markdown-table` 或 `format: json-schema`：

~~~json
{
  "version": 1,
  "templates": [{
    "path": "templates/profile.md",
    "field_ids": ["CD-D01", "CD-D02"]
  }]
}
~~~

必须从真实需求和已读材料生成完整 field_ids；上述两个字段只是语法示例，绝不代表真实14维只有两项。Markdown模板每个字段ID应位于**独立表格行的第一列**，允许标准GFM的行首/行末竖线省略、转义管道符与行内代码。**合法JSON Schema无需额外复制为Markdown模板**：`format: json-schema`（或文件名以 `.json` 结尾）时，默认每个 field_id 对应根 `properties` 下同名的可编辑属性；字段名不一致或分层时，显式指定 `field_paths` 的JSON Pointer（仅沿 `/properties/<字段名>` 层级，不执行外部 `$ref`）：

~~~json
{
  "version": 1,
  "templates": [{
    "path": "schemas/profile.schema.json",
    "format": "json-schema",
    "field_ids": ["CD-D01", "CD-D02"],
    "field_paths": {
      "CD-D01": "/properties/person/properties/appearance",
      "CD-D02": "/properties/person/properties/temperament"
    }
  }]
}
~~~

此例仅说明字段映射格式，不要求固定命名或固定14维；必须有各自可编辑属性（排除 `readOnly: true` 或 `const`），不能指向 `description`/`$defs` 冒充模板。最终 Skill 不放来源索引（§2b），spec 中出现 `source_index` 即返回 `SOURCE_INDEX_FORBIDDEN`。预检还拒绝已知来源记录文件和出处标记；它不能穷尽识别书名、人名、引文或隐含归因，§2b 的逐文件语义回读仍须完成，专业准确性也须人工复核。

~~~bash
python3 <KnowledgeCompilerRoot>/scripts/kd_delivery_preflight.py \
  --skill /safe/round/output/<real-skill-id> \
  --spec /safe/round/notes/delivery-preflight-spec.json
python3 <KnowledgeCompilerRoot>/scripts/kd_material_quality.py \
  skill --skill /safe/round/output/<real-skill-id> --host chatgpt
~~~

- 没有枚举模板的简单成果，不需要写空spec；原有skill校验和GQ1–GQ5依然适用。
- 该只读脚本检查字段是否独占一行、实际文本是否依赖notes/文件，并检查标准Markdown表格分隔行和列宽；另可按R09 §6.4在冻结前检查轮次收口一致性。通过仅返回 STATIC_ONLY_SEMANTICS_NOT_PROVEN，不代表观点正确、模板好用或实际模型成功。
- 目标宿主是ChatGPT才使用 --host chatgpt，不能只跑 --host generic 后宣称ChatGPT安装通过；实际加载与任务表现仍需要宿主测试。
- 缺少权限、失败或有争议时在**尚未冻结的同一Round**修复并复验；已冻结的历史成果不得回写。

## 7. 静态交付的轮次收口（按本轮授权启用）

只有在约定的静态检查已实际执行，且本轮按 R01 已具备终态资格时才启用 `round_closure`。**R01 的唯一正式轮次终态仍是“已完成”**；“静态交付”只是独立的验收范围，不创造另一种状态。

在 `notes/delivery-preflight-spec.json` 原有 spec 中增加下面的 `round_closure`。若无字段可用下列完整示例；已有 `templates` 时必须保留真实字段，不以空数组覆盖：

~~~json
{
  "version": 1,
  "templates": [],
  "round_closure": {
    "checklist": "checklist.md",
    "log": "log.md",
    "record": "notes/static-closure.json"
  }
}
~~~

`--round-dir` 必须指向正式 `rounds/round-NN-YYYY-MM-DD/`，`round_closure.checklist` 和 `round_closure.log` 必须分别为**轮次根目录**的 `checklist.md`、`log.md`，最终 Skill 位于其 `output/<real-skill-id>/`；不能用 `notes/` 中的控制文件副本或与本轮无关的目录。

实际 `notes/static-closure.json` 内容示意（不可照抄假摘要和假回执）：

~~~json
{
  "version": 1,
  "status": "STATIC_DELIVERED",
  "skill_tree_sha256": "<kd_material_quality.py skill实际返回的单份Skill身份SHA256>",
  "output_tree_sha256": "<kd_round_output.py --root round/output实际返回的完整output树SHA256>",
  "checks": [
    {"id": "host", "path": "notes/host-output.json", "sha256": "<真实回执文件SHA256>", "status": "PASS", "required": true},
    {"id": "gq", "path": "notes/artifact-quality-output.json", "sha256": "<真实回执文件SHA256>", "status": "EVIDENCE_REVIEW_REQUIRED", "required": false}
  ],
  "live_task": "NOT_RUN",
  "independent_review": "NOT_PROVEN"
}
~~~

在 `checklist.md` 顶部填写 `- 状态：已完成` 和独立的 `- 验收范围：静态交付`；在 `log.md` 追加 `状态：已完成`、静态验收依据、下面**两种不同算法**得到的摘要和遗留项：

~~~bash
python3 <KnowledgeCompilerRoot>/scripts/kd_material_quality.py skill \
  --skill /safe/round/output/<real-skill-id> --host chatgpt
# 其输出的skill_tree_sha256填写单份Skill身份摘要
python3 <KnowledgeCompilerRoot>/scripts/kd_round_output.py \
  --root /safe/round/output
# 其输出的tree_sha256填写完整output_tree_sha256
python3 <KnowledgeCompilerRoot>/scripts/kd_delivery_preflight.py \
  --skill /safe/round/output/<real-skill-id> \
  --spec /safe/round/notes/delivery-preflight-spec.json \
  --round-dir /safe/round
~~~

回执的 `version` 必须是整数 `1`，每个 `checks[]` 的 `required` 必须是 JSON 布尔值，不能省略或写成字符串。`live_task` 只接受字符串 `NOT_RUN` / `OBSERVED`，`independent_review` 只接受字符串 `NOT_PROVEN` / `OBSERVED`；其他类型或枚举值拒绝。

后者只核对 R01 的正式终态、验收范围、两种指纹、声明检查的JSON回执与其真实文件摘要/状态一致、required项必须PASS。由于两套树算法不同，不能将同一SHA复制到两字段。未运行的检查不得创造回执；即使预检PASS，也**不认证**模型调用、非作者身份、语义质量或GQ5，真实任务未运行继续记NOT_RUN/NOT_PROVEN。尚未达到静态交付时不启用round_closure，不提前冻结旧Round。
