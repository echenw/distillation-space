# R17 — 跨来源知识融合：从出处到可执行裁决

本文件是 R06 §3.2、§4 的**可选深化路径**。当多份真实独立来源提供不同方法、版本或相反主张，或用户要求把材料生成可用 Skill/Rule 时读。单来源短笔记、没有冲突的简单摘录不强制建表；不要用表格数量代表知识质量。

## 1. 四种来源/判断身份

| 标识 | 含义 | 限制 |
|---|---|---|
| F / SOURCE_OBSERVED | 当前固定版本中实际读到的文字、代码、工具回执，或用户明确确认的事实 | 需记范围与摘要；一次观察不等于所有场景必真 |
| H / DESIGN_INFERENCE | 基于 F 的原因解释、适用范围推论、材料之间的张力 | 不能升格成来源原话、确定性效果或用户已批准 |
| P / PROPOSED_OPERATION | 准备加入 Skill/Rule 的动作、分支、反例与输出合同 | 不等于已经执行、经过独立验证或获准正式知识写入 |
| USER_REQUIREMENT | 用户明确要求的字段、行为、权限和交付格式 | 不能把现代Schema/字段设计冒称来自古典文献或参考项目 |

F 可以是已确认的用户事实；此时其**设计归属**仍为 USER_REQUIREMENT，而非第三方来源。H/P 不因多数来源复述就自动升级为 F。历史版本分歧先按 R06 §3.2 配对对象、时点、范围和源码/文档权威。

使用 R05 的来源身份、R09 dossier 的原文行号、短引文和SHA核对 F；矩阵不引入第二套来源认证。没有用户授权时只整理候选，不扩张写入权限。已经经过独立准入的源不因跨书数量自动具备真实性或适用性的保证。

## 2. 本轮 notes/ 的最小融合矩阵

跨源复杂任务在本轮 notes/source-synthesis.md 留下每条**重要待采用行为**的决策；名称可变，不塞进正式 Skill。无需对每一句常识都建一行。

| 字段 | 必须能回答的问题 |
|---|---|
| requirement_id / owner | 哪项需求、由哪位消费者使用？原Skill已有怎样的等价行为？ |
| F / source | 哪些实际读过的来源与原文范围支持或反对？源ID、版本、摘要、许可是什么？ |
| H / contrast | 不同观点是互相矛盾、适用环境不同，还是只侧重点不同？哪些部分仍缺证据？ |
| decision | ADOPT / CONDITIONAL / RETAIN / REJECT / UNRESOLVED，并记录原因 |
| when / when_not | 什么时候应用或不能应用，谁能批准危险边界？ |
| counterexample / missing | 一条能推翻无条件套用的反例；证据不足时怎样安全退出？ |
| P / output_owner | 候选落入哪个Skill的哪节、哪个真实文件或操作，最终输出什么？ |
| proof_status | STATIC_CHECKED / ACTUAL_TASK_OBSERVED / NOT_PROVEN；注明实际回执或无回执 |

矩阵中的 ADOPT/CONDITIONAL 等标记只是**候选处理选择**，不是 R06 §3.2 规定的“已核实/待核实/按版本并存/经批准裁决”四种冲突核验状态，二者必须分别保留，不能用候选标记伪造已批准裁决。**同一决策行须写唯一明确的候选选择、成立条件和未采纳分支的理由**，不能只写“ADOPT 或 CONDITIONAL”而不作选择；尚不可解决的关键争议填 UNRESOLVED 并明确安全出口。

多个引文来自同一部原书不等于独立证据数增加。没有明确证据则 UNRESOLVED 或 NOT_PROVEN，不拼出貌似统一的第三条原则。该表为人工/Agent编纂辅助，不是自动冲突引擎，也不取代 R09 的素材与产物质量检查。

## 3. 裁决、反例与停止

1. **ADOPT：** 来源针对同一任务且适用边界相容，生成最短可执行动作；保留 USER_REQUIREMENT 与 SOURCE_OBSERVED 的不同归属。
2. **CONDITIONAL：** 两种方法因任务目标、信息量、宿主或版本不同而分别合理，写清选择条件及替代分支。不把“方法A总是有效”和“方法B总是有效”并列留给消费者猜。
3. **UNRESOLVED：** 来源时点、权限、原文关键页或运行结果缺失，暂停**依赖该争议**的结论，继续不依赖它的已许可安全部分。待决项不能进入正式规则。
4. **RETAIN / REJECT：** 现有行为已等价、来源项目专属、收益未证明或会增加不必要负担时不移植，保留可查理由；不要为了新增数量多而抛弃已验证的规则。

文学/设计偏好之间可能只是**不同侧重点**，不是可用事实判断谁真谁假；代码/API行为必须在同环境同版本下对照。重要冲突不能依据较新、较长、更多赞同或自动生成的评分裁决。

## 4. 一个合成例子：冲突意见如何转为消费者操作

**此处例子完全虚构，不是用户材料或可以提交到 dossier 的引文。**

假定用户要求一个章节修改 Skill。材料A建议“删去不推进主线的段落”，材料B建议“保留能塑造人物关系的日常细节”。

错误交付：“既要精练，也要有人情味”；或“自动删除所有冗余段落”。

可执行的 CONDITIONAL 决策：
- 输入：真实章节原文与本次修改目的；尚无原文时只提供检查清单，不假称读过。
- 当细节不改变人物目标、关系或之后的因果时，候选为删减；当细节改变关系状态、为未来选择建立代价时，候选为保留。
- 输出：建议删减/保留的原文定位、各自理由、可能失去的伏笔、请作者决定的歧义；没有改写授权只输出建议。
- H：按场景结果作条件划分是本次融合推断，不能说两位作者明确共同制定了该法。
- 反例：作者刻意的慢节奏实验不是“冗余”自动误删；条件不满足时不给确定性的删改结论。

## 4a. 知识深度保真：来源目录不是消费者规则

当用户要求从多份材料生产完整 Skill，**先完成可执行决策树，再整理模板**；出处记在本轮 notes/，不进最终 Skill（R18 §2b）。来源完整、字段完整、规则完整分别是不同的验收条件；不能用漂亮索引、更多引用或更少Token替代专业判断深度。

针对每项会影响结果的复杂需求，在当轮 notes/source-synthesis.md 保留下面的**真实决策链**（简单且没有条件分叉的任务可写明不适用原因）：

1. **可观察的任务情境**：输入与权威、版本、实际可得的证据；分清原文F、跨源推断H及用户自己要求的字段。不能用“所有作者都同意”掩盖来源张力。
2. **区分性判断**：从哪些信号判断选分支A而不是B？同时写出反信号、误判代价和来源不支持的情况；没有根据的阈值、强制规则及数字不得创造。
3. **可执行操作与反馈**：在分支A/B分别如何处理、读什么证据、给何种输出、何时请求作者裁决或暂停？适用范围不同并非某来源错误。
4. **反例、不可用和修复**：至少说明会推翻当前判断的具体反例，如何限制动作及如何复核修复没有破坏原约束。不要无条件把多个流派合成万能口号。
5. **消费者投影核对**：将上述真正会影响选择的条件、反例及失败出口写入**最终Skill实际被路由加载的reference/操作段**，记录这个目标文件与规则ID。只在 notes 的出处记录里列书名与一行摘要，不能替代完成的条件规则（出处本身不进最终产物，R18 §2b）；notes里的长笔记也不等于消费者能够看到。

**保真审查不是规则数量或字数竞赛**：多个真实来源可能只支持一条深规则，也可能需要数条互斥分支。对于14维字段等枚举需求，逐维填写是R18 §2a；逐维判断哪些证据支持、反驳、缺失以及哪些时点适用，是另一项专业知识义务。字段存在≠判断标准到位。对没有证据的领域显式标NOT_PROVEN，不编造成体系的反例。

合成例（不当作已读来源）：作者要检查人物某章突然背弃盟友。只用“人物动机必须一致”无法决定是否OOC；需分支检验“是否得知新信息、是否有强迫成本、过去是否有隐藏动机、叙述者是否不可靠、是否真正跨版本矛盾”。证据仍缺时应给可补的场景事实而非直接判崩坏。该条件树必须落到最终人物诊断操作，而非只保存在引用索引。

## 5. 不重复现有唯一权威

- 来源身份、可信边界与独立支持计数：R05；本矩阵不是 S01/SC01 或正式证据。
- 输入、版本和学习步骤：R06 §2–4；矩阵只在当前 notes/，行为只写目标Skill/Rule的唯一Owner。
- 需要证据绑定的核心主张：R09 §2 的中间 dossier 保存引文、行号与成品唯一锚点映射，不向成品插入出处标记；SHA正确不证明理解正确。
- 操作适用性和反例审查：R09 GQ4；不能自己填写独立GQ PASS。
- 新行为收益：R09 §4–5 和 R11；参赛作品、评分报告及其来源是**开发材料**，不能当成候选的全新独立holdout。
