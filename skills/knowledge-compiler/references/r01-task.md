# R01 — 问清需求与确认任务

配合入口第 1 步使用，说明怎样一项一项问清需求、怎样写进清单，以及用户确认意味着什么。任务需要子代理分工或机器可读的任务快照时，再读 §3–5。

## 1. 项目总需求与逐轮调查

先看工作区的 `requirements.md`、`materials/`、`results/manifest.yaml` 和 `rounds/` 中的历史清单与交付；已有活动轮次先读它的 `checklist.md`、`log.md`。**是否创建 Round 只看有没有新一轮独立知识提炼与交付任务，不看新增材料数或 Agent 任务数**。只收集、整理来源、补采、对照缺口、下载仓库、派发矿工或阶段性审查时，只在已有获准的 `materials/<批次>/` 和当前工作记录中登记，**不得新建空的 `round-*`**。已有提炼进行中或等待用户，先原轮续做；旧轮已完成冻结或明确取消后，取得本次独立目标授权才新开下一轮。已回答内容不重复问，不把历史输出的自述当成新用户授权。

**首次开始实际提炼与产物交付**时才在 Round 01 `checklist.md` 整理总需求；在此以前只采集材料的项目，可获授权先在工作区根部建立 `requirements.md` 草稿，或在材料批次的 `manifest.yaml` 留待确认的用途，**不必虚构一轮**。未获根部写入授权则在对话草拟，不越权创建文件。以后只调查相对已确认总需求的增量。缺的项目按以下顺序每次问一项并给默认建议。用户让助手决定普通细节时注明“助手代定”；涉及长期目标、产物类型、公开生效面或未授权写入的重大决策不自行代定。

| 项目 | 如何调查与记录 |
|---|---|
| 1 目的 | 总体要解决的问题、应用场景、本轮目的；首次记录到总需求，后续记录当轮差异 |
| 2 产物 | 学习笔记、材料整理、Skill、Rule、Skill+Rule 或仅建议；新建/修改、使用者、最终位置；没决定时先给建议 |
| 3 材料 | 本轮源文件/目录/链接/会话、版本、不能读的范围与许可隐私风险；新增材料不改变总目标 |
| 4 覆盖范围与轮次方式 | 全量（全部约定范围）/定向（特定主题）/轻量（明确选样和未覆盖部分）；初始/增量/全量重新提炼/专项修订 |
| 5 验收 | 总体验收（首次或长期要求改变时）和当轮逐条可核对的完成标准；是否在本轮更新 `results/` |
| 6 允许操作 | 记录当前任务与宿主的有效授权，默认读取指定材料、写获准任务目录；必要验证、其他源文件、`results/`、联网、付费、安装、Git 或发布分别核对实际覆盖范围，不重复询问已有许可，见 §2.2 |
| 7 深度 | 快速、标准（默认）、严格；见 §2 |

覆盖范围、轮次方式、学习深度是三条独立的轴，例如“**已完成首次交付之后的第二次独立增量提炼** + 全量覆盖新增批次 + 标准深度”。“初始/增量/全量重新提炼/专项修订”描述**本次交付相对上一版成果的性质**，不是采集任务或材料批次的序号。范围不明时明确写“待确认”，不能将没读的范围隐式当成全量；材料太多时收窄范围须记录未覆盖项并取得必要确认。

### 1.0 Round 开立判定（真实项目防误拆）

| 当前动作 | Round 决策 | 留痕位置 |
|---|---|---|
| 用户先找 45 个仓、再找 100 个仓、16 名子代理采集、四次补采 | **0 新轮**；纯收集尚未启动提炼时总 Round 数可为 0 | 按来源/时间建 `materials/<批次>/manifest.yaml`，只读原件；阶段摘要留材料批次工作记录 |
| 已启动 Round 01，用户追加十批材料或要求更多覆盖 | **继续 Round 01**；补输入版次，不建 Round 02 | 同轮 `inputs/revisions/manifest-vNN.yaml`、`notes/`、`log.md` 和清单 |
| Round 01 初稿被验收打回、子代理返工、失败用例重测 | **继续 Round 01**；冻结前可修改当轮草稿 `output/` | 同轮返工/复验记录，最终版通过才冻结 |
| Round 01 已完成且 `output/` 有可复核冻结指纹，用户明确要求新一轮独立修订并交付 | **创建 Round 02** | 新轮的 `checklist.md`、`inputs/` 与完整 `output/` |
| 用户明确取消 Round 01，之后另行委托独立任务 | **创建 Round 02**；取消轮保留历史编号，不算有效交付轮次 | 旧轮记录 `已取消` 与真实用户依据；新轮另记需求与权限 |
| 历史目录已误建多个采集 Round、输出为空或状态冲突 | **标记历史不合规**，不能擅自合并、移动、删除、改写旧目录来凑编号 | 记录事实、旧路径和消费者；另行取得授权后制定迁移映射 |

**硬边界**：提炼中的一个 Round 可跨多日/多会话/多批次，用户让 Agent 自主分阶段完成不等于授权多次提炼。若上一轮状态“进行中”但输出/日志矛盾，先核对真实字节、验收、指纹与原始授权；不把“日志声称完成”当作真实冻结，也不因“状态仍进行中”而无条件回写可能已被外部消费者使用的旧产物。

### 1.1 总需求 `requirements.md` 模板

```markdown
# 知识提炼项目总需求
- 当前确认版本：V1
- 状态：调查中 / 已确认
- 最近确认：<时间及真实用户消息定位>

## 学习目标与使用场景
...

## 总体交付
- 类型：Skill / Rule / 两者 / 文档 / 建议
- 目标位置与适用范围：...

## 总体覆盖与长期约束
- 范围与材料类别：...
- 长期要求、排除项和敏感边界：...

## 总体验收
- [ ] ...

## 版本变更
- V1：<时间> <确认依据> <原因/变动摘要>
```

`requirements.md` 是**当前已确认**的跨轮需求；首次未确认时可以是草稿，写入根目录须有对应授权，不能冒充已确认要求。长期目标、整体产物或长期规则变更时先依据原始用户指令重新确认；**若当前轮尚未完成，可在同轮更新并另存不可变的 `inputs/revisions/requirements-vNN.md`，不得因改需求强制多造一个轮次**。若原轮已经验收冻结且用户明确要求修改成果，再开始独立新轮。只是新增材料、改变当前轮覆盖方式或提出当前轮特例时，不改总需求。变更前须保留旧版的只读输入快照或可读取的固定 Git 版本；被 Git 忽略的工作区不能只写版本号。**总需求只保留一个当前有效版本与一处权威变更记录**，不同状态不能在同版中同时写“已确认”和“待确认”；任何实质变更记录新版本、确认依据与冻结快照，不把重复章节追加为另一套当前需求。

```markdown

- 流程：标准
- 状态：调查中
- 总需求：requirements.md V1

- 模式：初始 / 增量 / 全量重新提炼 / 专项修订（指独立交付方式，非采集批次）

- 本轮新增/特殊要求：...
- 本轮不适用项与原因：...

- [ ] 曾经失败的验收案例已针对最终版复验，或明确记未验证
```

首次实际启动提炼时，可以用一条完整用户请求同时确定总需求 V1 与 Round 01；已有有效消息覆盖目标、位置、操作和验收时，记录依据即可，不要求再批准助手整理的清单。**此前纯采集批次不算 Round 01**。下一次独立提炼只要求核对本轮内容和实质变化，不机械复用旧轮专属授权。取得根部写入授权并确认后，把当前总需求原始字节复制到本轮 `inputs/requirements.md`，在初始 `inputs/manifest.yaml` 写下 SHA-256、确认版本；快照只读、不可随后用新版覆盖。新增材料或需求改变但尚未冻结交付时，执行 §2.1 与 R06 §3.5 的同轮输入版本化；清单体现的是需求和权限，不是 G1 的正式知识写入批准。

## 2. 产物、状态、深度与权限

Skill 是按任务调用的可复用能力，Rule 是长期生效的约束；二者都要时分别确定触发、使用者、规则作用范围与路径，避免同一约束在两处维护。`rounds/<轮次>/output/` 是本轮独立最终产物，`results/` 是受控更新的当前累计产物。**累计成果必须按类型分开：Skill 放 `results/skills/<实际 Skill ID>/`，Rule 放 `results/rules/`，多份 Rule 按用途使用不同真实文件名；不得将 Rule 文件和 Skill 目录混放在 `results/` 根部。** 在成果清单中分别验收类型、名称、路径和使用者。已有混放结果按 R06 §4.13 经授权核实、备份、迁移及更新清单，不能擅自移动。选“建议”不代表获准编辑目标。

| 深度 | 做什么 | 限制 |
|---|---|---|
| 快速 `quick` | 材料整理和建议 | 不新建或改动 Skill、规则或正式源文件，不声称交付可用 Skill |
| 标准 `standard` | 形成自足产物，出处留中间记录，并静态自查 | 没有真实任务效果对照时保持未验证 |
| 严格 `strict` | 在标准上增加独立的真实任务对照 | 缺权限、模型或预算时标待验证，不用模拟数据代替 |

### 2.1 单轮生命周期

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| 调查中 | 已有明确独立交付目标，开始本轮提炼但需求尚未确认（纯采集不建轮） | 总需求和当轮清单确认且可固定材料时转已确认；缺用户输入可转等待用户 |
| 已确认 | 需求与授权可追溯，材料和总需求快照已冻结 | 开始真实阅读/提炼时转进行中；必要资源缺失转等待用户 |
| 进行中 | 按确认范围提炼、追加批次、制作草稿、验证或返工 | 本轮约定验收达到、所有使用输入版本可复核且核对非空输出清单及整树 SHA-256 后转已完成；阻塞转等待用户 |
| 等待用户 | 缺明确决策、材料、权限或必要资源 | `log.md` 记录此前阶段、阻塞点和接续操作；条件恢复后回到适用阶段，不能凭等候视作验收通过 |
| 已完成 | 本轮约定交付已完成、验收逐项有证据，`output/` 已冻结 | 终态；后续修改另开一轮，不能回写旧轮次交付；静态交付不代表真实任务或上线已验证 |
| 已取消 | 用户明确停止并取消本轮，原话/消息定位与现有工作状态可追溯 | 终态，不再自动续做；另有独立委托时开下一轮，不把取消轮当作已验收成果 |

- 每次状态变化**必须修改 `checklist.md` 顶部的 `状态` 字段并在 `log.md` 追加事实、实际验收和下一步**；勾选所有 `[x]` 或在日志写“收官/PASS”不等于轮次已完成。仍写“进行中”的轮次不得宣称冻结；`output/` 为空、没有真实文件摘要或存在未闭合阻断验收，不能转换为“已完成”。
- **静态交付的结束条件**：用户确认的本轮验收仅要求静态产物时，达到该验收、明确缺口并核对输出后可以记“已完成”。GQ1–GQ5 仍逐项按证据判定；未运行的真实任务、GQ5 和上线资格保留 `NOT_PROVEN`，轮次完成不表示 Skill 全面合格，也不增加采纳、安装或发布权限。
- **取消的记录与边界**：只依据真实用户明确取消/终止本轮的指令记“已取消”，在 Checklist 顶部写 `- 取消依据：<真实停止消息定位>`，并在 Log 保存原因、实际变更及未完成项。保留已有输入和草稿，不补造完成验收或冻结指纹，不将取消轮成果采纳到 `results/`。取消轮占用历史编号，后续新轮仍递增；它计入目录总数，但不计活动轮、完成轮及 `--expect-rounds` 的有效轮数。不能通过删除目录、伪造取消或把临时等待改成取消来过预检。
- 需求或材料在确认后变化，先记录影响；实质范围变化重新取得必要确认，**不得覆盖任何已冻结的初始输入**。在同轮 `inputs/revisions/manifest-v02.yaml` 等不可变版本保存**截至该版全部有效来源及其真实摘要**，写前版 manifest SHA-256；若总需求改变则另存 `inputs/revisions/requirements-vNN.md` 与其 SHA，`checklist.md` 指向最新有效版本。每份输入版本均应可回读；新增材料不是开新 Round 的触发条件。已经完成的轮次不回退。
- `results/` 的“未合并/已合并”**不是**轮次状态：完成后可以不合并；首次采用成果与后续合并依 R06 §4.13，合并时由 `results/manifest.yaml` 的实际版本和来源记录证明。
- **输出指纹**：验收时列出 `output/` 下全部普通文件的相对 POSIX 路径及原始字节 SHA-256；拒绝符号链接、特殊文件与越界路径。路径按 UTF-8 字节序排序，每项串接 `path + TAB + sha256_lower_hex + LF`（均为 UTF-8），连接所有行后取 SHA-256 为整树指纹。用下述只读工具返回的 `files` 和 `tree_sha256` 填入本轮 Checklist 冻结区，并在 `log.md` 记录完成时间。后轮引用旧输出前使用 `--expected` 复核，不一致即停用该基线并调查；已完成轮次不回写。因为任务目录可能被 Git 忽略，**同目录里的自填指纹不构成防篡改证明**；如需可独立追溯，另经授权保存外部只读快照或 Git 版本。

```bash
python3 <SkillRoot>/scripts/kd_round_output.py --root /safe/distillation/rounds/round-01-YYYY-MM-DD/output
python3 <SkillRoot>/scripts/kd_round_output.py --root /safe/distillation/rounds/round-01-YYYY-MM-DD/output --expected <已冻结的整树 SHA-256>
```

此脚本只读，以不跟随链接的文件描述符核验文件身份与读取期间的变化，拒绝硬链接和已观察到的并发替换；它仍**不是原子文件系统快照**，并发写入或外部修改可能让任何扫描结果失去历史证明力。验收/重核应在停止写入的工作区或可信只读快照上执行；脚本不会冻结权限、创建备份或批准结果。**特别禁止使用后续阶段直接编辑前轮的已冻结 `output/` 作为返工区**：没冻结的工作稿归当前轮，已冻结的输出只能只读作为新一轮输入基线。

**工作区收口预检（只读，获准运行时）**：

```bash
python3 <SkillRoot>/scripts/kd_workspace_audit.py --workspace /safe/distillation
python3 <SkillRoot>/scripts/kd_workspace_audit.py --workspace /safe/distillation --expect-rounds 1
```

该命令检查多轮同时未收口、宣称完成却空输出/缺指纹/有 SHA 漂移、同轮输入版本链、累积成果清单的逐文件摘要和分类；例如“十批材料仅一次交付”，`--expect-rounds 1` 可揭露错误新建十轮。Checklist 的状态、流程、取消依据、冻结与输入摘要等控制字段，以及受检 manifest 的同级关键字段必须唯一，重复即拒绝；历史变化写在进度或日志中，不复制另一套当前控制值。`rounds_total` 包含保留的取消轮；`rounds_counted` 与 `--expect-rounds` 排除已取消轮，因此“取消一轮后重新委托一次交付”的期望有效轮数是 1。返回结构化 JSON 的 `PASS` (exit 0) 或 `FAIL` (exit 2)，**不会创建、移动、删除或修复任何文件**。预期有效轮数来自实际用户委托，不能由脚本猜测；静态检查也无法认证用户身份、材料真伪、真实行为验收或 YAML 全部语义。运行条件不具备时记录 `NOT_PROVEN`，不以跳过命令冒充检查通过。

### 2.1a 单次短笔记（不进入正式晋升）

当用户仅要一份明确来源的短笔记或材料整理、不要求跨轮继承、规则/Skill 编辑、更新 `results/` 或正式入库时，可按入口 §2.1a 直接用一条已明确的用户指令启动；缺必要来源、路径或权限时只问真正缺失项。只为该短笔记开一轮，在 `checklist.md` 简记目标、来源版本/实际阅读范围、权限、验收、用户消息定位，在 `log.md` 简记结果，正文留在 `rounds/<轮次>/output/`。不要求项目总需求文件、其 SHA 副本、材料批次索引或整树冻结摘要，也不得假报这些机制已经执行。不得覆盖旧轮输出或改 `results/`；若以后要成为跨轮基线，重新按 §2.1 固定输入和完成检查。

轻量 Checklist 必须保留下面的流程字段，预检据此识别轻量路径；标准任务使用 `- 流程：标准`，不能改标签来跳过标准验收。

```markdown
# Round <编号> — 短笔记
- 流程：轻量短笔记
- 状态：调查中
- 用户需求与授权依据：<真实消息定位>
- 目标与输出：<短笔记目标及 output/ 内路径>
- 材料与已读范围：<来源、版本及实际范围>
- 允许操作：<本轮实际授权>
- 验收与未核项：<达到情况、证据及限制>
```

完成后将顶部状态改为“已完成”并在 Log 留下实际交付依据；用户明确取消则按 §2.1 记“已取消”。轻量路径不交付 Skill 或 Rule，预检遇到 `SKILL.md`、`AGENTS.md` 入口会拒绝该豁免；其他名称的产物仍须人工核对用途。

### 2.2 权限与确认

本轮 Checklist 的“允许操作”记录用户确实同意的内容，不能把写 `rounds/` 的许可扩展成创建/改写根目录 `requirements.md`、`AGENTS.md`、`README.md`，或改写 `results/`、个人/全局规则和正式知识库。初始化工作区时可一次取得这些位置的明确授权，后续仍不得据此推定更新 `results/` 的权限。更新 `results/` 前单独核对当轮目标、实际授权、当前版和冲突；正式知识库仍需要 G1/S12。

执行前先核对当前任务、原始用户消息和宿主权限；已覆盖本轮且仍有效的授权持续适用，必要的本地验证按适用权限执行，不因换会话、追加记录或整理清单要求重新批准。缺失且会影响执行的权限或关键决策才向用户询问，未获授权的部分暂停，不依赖它的已授权工作继续。个人全局配置、付费调用、生产写入、安装、Git 提交和发布仍分别核对其授权，Skill 本身不授予这些能力。

用户确认是对本轮目标与权限的确认，不是经过认证的用户身份、G1 批准或宿主可执行能力。找不到原始确认消息就记缺失，不伪造。变更要求若影响总体验收或长期规则，先核对真实的新用户要求并记录确认依据；旧授权不自动覆盖新增范围，不相关的普通细节自主处理。

## 3. 单人执行或子代理分工

默认由一个 Agent 完成。只有工作能拆成输入不同、互不争写同一文件、确实可以并行的几个单元时，才考虑子代理。

- 主代理负责向用户提问、统一计划、整合冲突和全部写入。子代理只做材料提取、交叉核对、方案草案或独立复核，角色是 `extract`、`cross_check`、`plan`、`review` 之一。
- `single` 适合来源不多、任务集中在同一批文件、宿主没有可靠的子代理能力，或者并行只会带来重复阅读的情况。
- `auto` 在用户没有指定时使用。独立工作单元少于 3 个，或者宿主的子代理能力未知，都按单 Agent 执行。
- `parallel` 需要同时满足三点：用户明确要并行，`host_max_agents` 和 `budget_max_agents` 都填了明确的正整数，任务之间互相隔离。缺任何一点时，建议器返回单 Agent，已确认的并行计划会被拒绝，应当退回 `single` 或补全上限。涉及付费模型时，还要另外确认实际的金额预算和付费授权；脚本不另设 16 个 Agent 的通用硬顶，数量受显式宿主容量、预算和独立工作单元约束。
- Agent 数量的上限把主代理算在内。`kd_task_brief.py recommend` 只计算建议的数量，不会启动 Agent、修改文件，也不保证宿主真的启动了它们。
- 工作单元数不另设 1000 的通用硬顶；机器快照仍受 JSON 字节和嵌套资源上限保护。声明数量只参与算术检查，不按它预建 worker 集合；确认计划仍必须逐项列出真实工作单元和全部分派。
- 每个子代理记录 `worker-1` 这样的身份、所属工作单元和角色，能读的材料不得超出所属工作单元。计划里只要有模型请求，所有发起请求的 Agent（包括 lead）都要在 `model_routing` 里写明 `model` 和 `max_context_tokens`，否则 `kd_execution_review.py` 拒绝验收。`max_cost_usd` 是声明的费用上限，真实的 Token 和费用仍要由宿主取证。
- 主代理对没有分派出去的工作和最终修改负责。写候选的 Agent 不得读取独立评测的保留答案，子代理的审阅也不等于人工批准。
- 运行前宿主限制或预算有变，已确认的 Agent 数量无法执行时，应当退回单 Agent，并重新记录变更后的方案。只是普通技术取舍、原授权仍然覆盖时，记下偏差和原因即可，不要声称启动过并未启动的子代理。

## 4. 按需保存任务快照

普通任务用 `checklist.md` 和 `log.md` 就够了。只有需要子代理编排，或者要用脚本核对计划有没有被改动时，才额外保存机器可读的任务快照。`task-brief.vN.json` **只覆盖下方已映射的单轮字段**：总需求版本、覆盖范围、轮次方式、`results/` 合并决定和输出冻结指纹仍以本轮 Checklist 及实物为准，`kd_task_brief.py` 不验证它们，不能写成两份记录已完全等价。

快照放在任务目录里，第一份叫 `task-brief.v1.json`，之后每次变更追加 `task-brief.v2.json`、`v3`，不要修改旧版本。`checklist.md` 仍是需求与权限的完整依据；两者重叠字段必须一致，超出 JSON Schema 的字段不伪称已自动核对。`scripts/kd_task_brief.py` 只做只读检查，不写文件：

```bash
python3 <SkillRoot>/scripts/kd_task_brief.py check --input /safe/brief.json
python3 <SkillRoot>/scripts/kd_task_brief.py prepare --round /safe/distillation/rounds/round-01-YYYY-MM-DD --input /safe/brief.json
python3 <SkillRoot>/scripts/kd_task_brief.py inspect --round /safe/distillation/rounds/<任务名>
```

清单项目和快照字段这样对应：

| 清单项目 | 快照字段 | 说明 |
|---|---|---|
| 学习目标 | `plan.objective`、`success_definition`、`non_goals` | 目标、成功标准和明确不做的事 |
| 最终产物 | `plan.output`、`plan.deliverables` | `output` 取 `materials_only`（学习笔记、材料整理）、`skill`、`rule`、`both` 或 `recommend`。每个产物的 `action` 是 `propose`、`create` 或 `update`。规则的 `surface` 是 `project_rule`、`host_global_rule` 或 `knowledge_rule`，其中 `knowledge_rule` 只能 `propose`。不同产物不能指向同一个路径 |
| 学习材料 | `plan.materials` | 每份材料有 `id`、`locator` 和 `snapshot_sha256`。确认新建或更新产物前必须锁定摘要，更新已有目标还要 `target.before_sha256` |
| 完成标准 | `plan.acceptance` | 逐条可核对的标准 |
| 允许的操作 | `plan.requested_permissions` | 只记录申请的能力，不是授权 |
| 学习深度 | `plan.depth` | `quick` 的已确认计划只能包含 `propose`，也不能申请编辑、安装、生产写入或发布权限 |
| 分工 | `plan.agents` | 见 §3 |

**此 JSON 不编码的本轮信息**：覆盖全量/定向/轻量、轮次方式、总需求版本及摘要、是否将成果纳入 `results/`、`output/` 冻结指纹；这些仍必须读取 Checklist、`inputs/manifest.yaml` 和实际文件核对。不可因 `kd_task_brief.py inspect` 通过就声称上述信息已通过机器校验。

知识库的 `global` 适用范围和用户的全局配置文件是两回事，不要混用。

`state` 有两种取值。`draft` 不需要确认。`confirmed` 必须带上用户确认消息的定位、摘要，以及和计划内容绑定的 `plan_sha256`；`recommend` 还没有定下产物，不能进入 `confirmed`。脚本对已确认的快照返回 `ADVISORY_CONFIRMED_REFERENCE_UNVERIFIED`，意思是文件声称已确认并且字段一致，脚本并没有核实真人。执行前宿主仍要核对原始确认消息、实际权限和材料版本。

`revision` 从 1 开始逐个递增，`previous_sha256` 记录上一版文件原始字节的摘要。目标、材料、产物、Agent 数量或权限有变化时，先追加新的 `draft`。当前 `prepare` 对计划变化后的 `confirmed` 要求新的真实 `user_message_ref`，不能引用**全部历史确认消息**中任何一条用过的确认定位；这是机器快照的现有契约，不是对实际权限的认证或撤销。已有授权仍覆盖普通调整且没有新确认消息时，保留新版 `draft`，在 Checklist/Log 记录变更和真实授权依据，按原始用户要求与宿主权限继续；不得为快照捏造消息、机械要求二次审批，或拿旧 `confirmed` 的 hash 冒称新计划。新增范围或关键决定缺授权时，才向用户取得必要确认并绑定新版 `confirmed`。输入材料和需求变化仍须按 §2.1 保存不可变输入快照；此出口不绕过 G1/S12。计划没变的重复提交仍由宿主核对真实消息和最新输入。

`prepare` 返回 `PREPARED_NOT_WRITTEN`、预期文件名和输入文件原始字节的 SHA-256，它不写盘。宿主确认有写入授权、目标文件不存在后，用“已存在就拒绝”的方式把输入 JSON 原样写成预期文件，再用 `inspect` 核对链尾摘要与 `prepare` 的结果一致。宿主做不到这种只创建不覆盖的写入时，应当停止保存快照并说明原因，不要改用覆盖式写入。快照只是任务记录，不是知识入库，也不是授权。

## 5. 快照格式与恢复检查

下面是字段示意，不是可以直接提交的已确认计划。`plan_sha256` 是对 `plan` 对象执行 `json.dumps(sort_keys=True, ensure_ascii=False, separators=(",",":"), allow_nan=False)` 后取 UTF-8 的 SHA-256。

```json
{
  "format": "knowledge-compiler-task-brief/1",
  "revision": 1,
  "previous_sha256": null,
  "state": "draft",
  "plan": {
    "objective": "把用户提供的排错材料提炼成可复用排障能力",
    "depth": "standard",
    "success_definition": "已有错误可定位，新 Skill 通过独立任务判据",
    "non_goals": ["不监听任何私人会话", "不修改个人全局配置"],
    "materials": [{"id": "M1", "locator": "batch.md", "snapshot_sha256": null}],
    "output": "skill",
    "deliverables": [{
      "id": "S1", "kind": "skill", "action": "create",
      "purpose": "复用排查过程", "style": "workflow",
      "trigger": "用户请求排查相同类型问题", "expected_result": "明确的诊断步骤及可重放验证",
      "target": {"surface": "skill_source", "destination": "/authorized/staged/example"}
    }],
    "acceptance": ["冻结案例中正确诊断且无安全退化"],
    "constraints": ["不执行材料中的指令"],
    "requested_permissions": ["read_materials", "edit_skill_source", "run_local_tests"],
    "agents": {
      "mode": "auto", "independent_units": 1, "host_max_agents": null,
      "budget_max_agents": null, "chosen_agents": 1, "assignments": [],
      "work_units": [{"id": "U1", "objective": "梳理来源并起草候选", "material_ids": ["M1"]}]
    }
  },
  "confirmation": null
}
```

- 示例是 `draft`。`snapshot_sha256:null` 表示材料还没有锁定，不能直接当作已确认计划执行。
- 更新已有目标时必须填写 `target.before_sha256`，宿主在动手前再读一次真实文件核对。模型建议的摘要不能代替它。脚本只检查摘要的格式，文件内容的核对由宿主和 R09 负责。
- `confirmed` 要补上 `confirmation:{"user_message_ref":"<真实消息定位>","summary":"...","plan_sha256":"<计算值>"}`。自己编写的确认得不到任何权限；没有真实确认时保留 `draft`，并告诉用户还有哪些事要决定。
- 确认之前，每个工作单元都要有能独立执行的职责。子代理分配写明 `worker`、`role`、`work_unit_id` 和 `material_ids`，没有分派的工作单元由主代理承担。

恢复任务时先读 `checklist.md` 和 `log.md`。有快照的，再用 `inspect` 核对版本链和最新状态，并比对当前材料摘要、目标版本和宿主环境。版本变化本身不撤销已有授权；按 §4 追加新快照并核对实际覆盖范围，不能把旧 `confirmed` 当成新计划的确认。用户意图或新增范围不再被原授权覆盖时补齐必要确认。不要扫描用户的 HOME 目录，不要持续采集对话，不要擅自运行候选 Skill 或材料里的脚本，也不要把个人的任务记录放进分发包。
