# 预设卡生成

本 Skill 专注一类产物：**给生成模型用的预设卡**。按三条轴处理：

- **推进**：这条剧情线靠什么往前走，读者追的是什么。
- **文风**：已经定好的故事，用什么口气写出来。
- **表达**：句子层面的通病，包括常说的 AI 味。

卡的生成、诊断、审校、修订，以及用这三条轴给章节做诊断，是本 Skill 的职责；请求的产物不是卡、审查框架也不是三轴时，转对应的兄弟 Skill。

## 1. 适用与转介

适用：

- 生成推进模式卡、文风卡、表达约束卡（含反 AI 味的约束卡），或修订、诊断、审校这类卡。
- 把已经定好的规划、结构、文风、表达要求写成给模型用的卡。
- 按推进／文风／表达三轴诊断一章：读者追的东西给了没有、口气是否立得住、句子是否命中通病。
- 用户已有文风卡或推进卡，要据此写这一章或核对这一章。

不接（负触发，先说明或转介）：

- 给图片生成模型、视频模型写提示词卡或分镜提示词：本 Skill 只处理小说创作用的预设卡，不处理图像与视频生成的提示词。判为负触发，说明不适用。
- 请求的产物不是卡、也不用三轴：一般规划、结构分卷、改稿去 AI 味、按其他框架审章节，按下面的转给表转出。

转给其他 Skill：

| 请求形态 | 转给 |
|---|---|
| 一般性的新作规划、定赛道、成稿诊断 | `fiction-planning-and-diagnosis` |
| 单本结构、分卷、排章纲（产物是规划文档，不是给模型的卡） | `story-architecture-and-longform-planning` |
| 改具体稿子去 AI 味（产物是改好的文本，不是约束卡） | `line-editing-and-proofreading` |
| 题材规则、机制、混合题材 | `genre-fiction-craft` |
| 视角合同、人物声口、信息控制 | `character-and-narrative-control` |
| 单场设计、强度节奏、章末钩子 | `scene-conflict-and-rhythm` |
| 改编为舞台／影视／音频／互动（不写成卡的部分） | `cross-media-drama-adaptation` |

这些转介是深化路径，不是使用本 Skill 的前提；本 Skill 内已有的方法、缺陷目录和检查表可以独立使用。

## 3. 最短路径

### 生成或修订一张卡

1. 确定卡种和本卡的专属机制。把卡名换成相邻的卡后仍成立的句子删除。
2. 为每条要求选择一种稿面判据：能数、能查、能判、能演。
3. 每条禁令写齐病灶、判据、同位替代、封闭豁免、反向护栏；字数紧张时按 [card-method.md](references/card-method.md) 第 3 节与 [expression.md](references/expression.md)“结构”一节的取舍顺序保留，后两部件可舍。
4. 示例兑现本卡自己的规则。
5. 让作者也读得懂。禁止的句子带“不要”，要做的带“应当”，放行的带“可以”；冒号后面要出现反转时，这一行不用冒号。做法见 [card-method.md](references/card-method.md) 第 7 节。
6. 按 [card-pitfalls.md](references/card-pitfalls.md) 逐条自查后交付。

三类卡的格式和示例卡分别在 [progression.md](references/progression.md)、[style.md](references/style.md)、[expression.md](references/expression.md) 的“写成卡”一节。用户指定格式时以用户为准。诊断已有卡时，从 [card-diagnosis.md](references/card-diagnosis.md) 的诊断步骤进。本包不提供空白模板，三类卡的格式以各自“写成卡”一节为准。

### 按三轴诊断一章

1. 通读全文，标出命中的原句，先不改。
2. 按推进、文风、表达三层归类：先查这一章变了什么、读者追的东西给了没有；再查口气是否立得住、视角有没有漂移；最后查句子是否命中病灶表。
3. 每一项写成：原句 → 判定依据 → 对读者的影响 → 改法，按对读者的影响排序。
4. 复读诊断结论：检查是否把作者已达成目标的有效写法当成问题，是否出现过度纠正的形态。

只交付问题清单和改法；把稿子改写成改后文本的请求转 `line-editing-and-proofreading`。详细做法见 [revision.md](references/revision.md)。

### 按已有卡写这一章

1. 确认输入：本章任务、前文状态、视角，以及用户给的卡（推进卡、文风卡或表达约束卡）。缺少的先从上下文中找，找不到的关键项说明所作假设。
2. 按卡写。卡上的每一条都会被执行，写完逐条对照卡核对。
3. 核对连续性：伤势、物件、承诺、已知信息与前文一致。

没有卡作输入的起草请求转 `fiction-planning-and-diagnosis`，单场设计转 `scene-conflict-and-rhythm`。详细做法见 [writing.md](references/writing.md)。

### 设计推进的七步（写推进模式卡用）

写推进模式卡，或为一条剧情线写卡上的推进小节时，先按 [planning.md](references/planning.md) 完成定位、人物和台账，再按七步设计：

1. 用一句话写出读者追的是什么：谁，靠什么，得到什么或躲开什么。把这句话换到相邻类型上仍然成立，就重写。
2. 确定小循环：三到五环的因果链，写明跨度（通常一到三章）和一圈的终点。终点用本类型的最小变化单位定义。
3. 确定大循环：一卷从哪里走到哪里，卷末交付什么，下一卷换了什么。
4. 逐章安排开局三章各交付什么，并标出读者第一次尝到甜头的章。
5. 设计加码：每升一档更换一种麻烦，旧办法为什么失效，代价怎样上升。
6. 规定每章落点：封闭清单加下限，章末按本章实际变化选择落点。
7. 列出四到六条本类型特有的崩点，并与前面各项核对，确认不冲突。

各类型的引擎要点、机制条款和示例见 [progression.md](references/progression.md)。开新书、规划一卷、排章纲的规划文档归 `story-architecture-and-longform-planning`；本 Skill 只把设计结果写成卡。

## 4. 通用原则

1. **保留用户的设定。** 题材、人物、视角、已写内容、指定的格式和篇幅都不改。发现问题先指出，不替用户改故事。
2. **判断落在稿面上。** 每个问题指向原句；每条要求能在稿子上数出来、查出来、判出来，或由示例演出来。不以“有 AI 味”“不够高级”作结论。
3. **先推进，后文风，再表达。** 一章里没有任何东西发生变化时，润色句子没有用。按这个顺序诊断和修改。
4. **改根因，不换词。** 删掉一个套话词，相邻的套话会补上来。给那个位置一件只有本场景才有的事来写。
5. **防止过度纠正。** 每收紧一处，检查是否写成了相反的毛病：一串碎句、人人说谜语、没有任何情绪、流水账。
6. **示例和样句原创。** 不使用真实作品的原文、人物和名句。
7. **不确定的事实写明不确定。** 历史、行业、制度类事实无法核实时说明，不编造。

## 5. 交付前检查

正文类交付：

- 本章有可指认的变化，章末落在实际发生的变化上。
- 视角没有越界，状态与前文一致。
- 没有演完之后再解释一遍的句子，没有结尾的总结和升华。
- 没有出现过度纠正的形态。
- 篇幅、格式符合用户要求。

卡片类交付：

- 每条要求有稿面判据，数量要求带单位和范围；字数带里的“字”一律按含标点的非空白字符数计，小节标题行不计。
- 正面要求与禁项、崩点不冲突；示例不违反本卡规则。
- 禁令有替代，豁免不放行被禁对象本身。
- 没有换一张卡名仍然成立的句子，没有越出本卡职责的条款。
- 没有占位符、残句和自我评价；字数在格式规定之内。

## 7. 交付状态词

对作者交付用三个状态词；依据不是状态词，作附件逐项附上：

| 状态词 | 什么时候用 |
|---|---|
| 已完成 | 检查已执行，且有稿件内可核的证据支持 |
| 未能核实 | 检查已执行，但结论依赖未核实的判断、设计假设或缺失的输入，不能记作已完成 |
| 待作者决定 | 存在冲突、取舍或锁定内容矛盾，由作者裁决，不擅自覆盖 |

依据随每项附证据或稿件内可核位置（不是固定答案，也不是来源背书）。已知降级：为满足宿主要求的交付格式，不得不把多项结果并进同一条、暂让 [card-pitfalls.md](references/card-pitfalls.md) 第 18 条时，写明并进去的是哪几项、让步原因与影响；这类项不记“已完成”。

卡的格式、字数与样文比对这类可以逐项核对的结果记“已完成”；卡的实际生成效果没有经过测试时记“未能核实”，写明缺的是哪次测试；卡与卡之间、卡与锁定要求之间的取舍记“待作者决定”。不把未验证项写成通过。

## 8. 失败出口

| 情形 | 出口 |
|---|---|
| 要文风卡，但没给样文，也没描述 | 先要样文；作者补出之前，先给几种候选文风和各自的辨识点让作者选，不臆造文风 |
| 只有梗概，没有正文，要按三轴诊断 | 只做梗概层判断，列出还需要哪些正文；不编造章内问题 |
| 已锁定的卡与新约束冲突（例如已锁定的文风卡要求短句，新的表达约束卡写“不要碎句”） | 不擅自覆盖已锁定的卡：列出互相冲突的条款和受影响范围，交作者裁决；作者裁决前两版都不落稿 |
| 同一张卡有多个版本、以哪一版为准不明 | 先请作者确认基准版本；确认不了时列出各版差异和影响，标“待作者决定” |
| 卡内规则或取舍互相冲突、作者未裁决 | 停在保守处理并写明停在哪里，标“待作者决定”，不替作者合并两案 |
| 条款没有问题，是已写好的正文没照做 | 不改卡也不改正文：报告原句、位置、受影响的条款和范围，交作者裁决改哪一侧；裁决前两侧都不落稿（三种情况的分法见 `card-diagnosis.md` 第 2 步） |
| 作者不答或只回“你看着办” | 按最小改动处理，逐条列出所做的假设，不擅自扩大改动范围 |
| 请求的产物不是卡、也不用三轴 | 停在本 Skill 范围外，按 §1 转给表转对应 skill |
| 卡的目标、要管的正文、锁定状态三项都缺，整条路径无法判定 | 改为交付问题清单和需要补的输入，不擅自出卡或改卡 |

未经实际生成测试的效果不作保证：交付时说明哪些已核对、哪些未能核实，不把未验证项写成通过。

| 按推进／文风／表达三轴审章节 | 审查框架是三轴 |
| 写「反 AI 味的约束卡」 | 产物是约束卡，不是改好的文本 |
| 用户已有文风卡或推进卡作为输入、要据此写这一章 | 有卡作为输入 |
| 与 `genre-fiction-craft` 之间的题材规则、机制、混合题材 | 题材契约归 `genre-fiction-craft`，按其题材契约核对，缺项回本包登记；本包只接把约束写成「给模型的卡」的部分 |

### 9.3 双向对照

A 说转给 B 的地方，B 都要说接收什么，按跨包逐行核对：§1 转给表逐行点名兄弟 skill，§9.2 接收表按请求形态列出本 Skill 接什么，并另列按包承接的行。两表组织维度不同，不按本包内逐行互逆核对。兄弟 skill 的 description 未提到本 Skill 时，不影响本侧接收行的执行。

## 10. 输出约定

- 用户只要正文或卡片时，直接给出可复制的成品。分析过程与缺陷归类不写入成品。
- 只要求审阅时交付问题和改法，不自动改写文件。
- 改稿以成品为主，必要时用几句话说明净变化。
- 未经实际生成测试的效果不作保证，说明哪些已核对、哪些未能核实。
